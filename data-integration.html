5 · Data Integration Challenges

"Three separate source systems in three different formats — CSV for orders, JSON for customers, SQL database for products. These systems don't communicate with each other."
Client Value

Heterogeneous source systems are the norm in any real business. The pipeline doesn't force source systems to change — it meets each source on its own terms and normalises everything into a single queryable model. Once in Gold, a BI analyst never needs to think about whether a fact came from a CSV or a database.

No changes required to existing source systems Single unified Gold layer regardless of source format Each source system isolated — one failing doesn't cascade
How the Pipeline Addresses It

Each source type has its own dedicated ingest module with format-specific logic, each producing the same Bronze Parquet output format:

  • ingest/orders.py — reads CSV via pd.read_csv(), adds metadata, writes partitioned Parquet
  • ingest/customers.py — reads nested JSON, flattens address.city / address.country inline, writes Parquet
  • ingest/products.py — connects to SQLite, runs watermark-filtered SQL query, writes Parquet

After Bronze, all three sources are in the same format and processed by the same Silver and Gold logic. The integration complexity is fully contained within the three ingest modules.

SQLite (products) → ingest/products.py → Bronze Parquet
Engineering Deep Dive

Why flatten JSON at Bronze, not at Silver? Bronze should be a faithful representation of the source for replay purposes, but nested structures in Parquet require schema-on-read handling that complicates all downstream stages. Flattening at ingest normalises the structure once and makes Silver/Gold logic identical across all sources.

Why SQLite with a watermark vs full extract? Full extract of a product database on every run is wasteful for large catalogs and also misses the meaning of incremental updates. The watermark pattern only fetches genuinely new/modified rows, matching the CDC (Change Data Capture) semantics of the source — products table records when each product was last modified via updated_at.

Stage isolation in pipeline.py: each ingest is a separate stage() call. If the SQLite products DB is unavailable, only ingest_products fails. Orders and customers still ingest successfully. This is not the case in a monolithic script — one failure would kill everything.

Suggested Improvements
Quick Win

Add a source connectivity check at pipeline startup before any stage runs. If products.db is unreachable, fail fast with a clear error rather than discovering it mid-run after orders and customers have already written Bronze.

Quick Win

Move JSON flattening logic to a config-driven field map (e.g. "address.city" → "city" in pipeline.yaml). Currently flattening is hardcoded in customers.py — adding a new nested field requires a code change.

Next Step

Add retry logic to ingest stages for transient failures (network timeouts, locked SQLite file). Currently any exception halts the stage with no retry. Exponential backoff with 3 attempts would handle transient issues automatically.

Future

CDC via Debezium: replace the SQLite watermark pattern with a proper change-data-capture connector that streams product changes into Bronze in near-real-time, eliminating the batch polling interval entirely.
